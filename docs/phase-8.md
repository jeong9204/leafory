# Phase 8 — PWA 설치·오프라인 및 모바일 테스트 준비

검증 날짜: 2026-10-27.
Phase 7은 `c3ab1e808177d76e04a4c669e71207cbe25bd8b4`
(`feat: add plant care calendar`)로 커밋·push했습니다. 해당 시점에 원격/로컬 main 일치와
깨끗한 작업 트리를 확인했습니다. 아래 Phase 8 변경은 기능 구현 검토 후 별도 마무리
커밋(`feat: add PWA support and optimize loading`)으로 정리합니다.

## 캘린더 조정

날짜 행의 최소 높이를 56 → 48px, 숫자/점 간격을 6 → 4px로 줄였습니다.
5주 달력은 약 40px, 6주 달력은 약 48px 공간을 확보합니다.
320px 실제 viewport에서 날짜 버튼 44×48px, scrollWidth 320px를 확인했습니다.
390px도 가로 넘침이 없으며 색상·점·월 이동·필터와 접근성 키보드 동작을 유지합니다.

## 설치 설정과 아이콘

- `public/manifest.webmanifest`: Leafory 이름, 고정 앱 ID `/`, 시작/범위 `/`,
  `display: standalone`, 크림 배경/테마 색상, 한국어 설명.
- 192/512 PNG(any), 512 maskable, 180 Apple touch icon, SVG favicon을 추가했습니다.
  아이콘은 직접 작성한 SVG 잎 그림을 PNG로 렌더링했으며 외부 이미지나 폰트는 없습니다.
  maskable의 중요한 그림은 중앙 안전 영역에 있습니다.
- HTML에 Manifest·Apple touch icon·iOS 메타데이터를 연결했습니다.
- 홈에서 `/install` 안내로 이동합니다. Safari/Chrome 설치 방법, 준비 완료 상태,
  오프라인 가능 범위와 백업 이동 안내를 제공합니다. 설치 여부는 기기의 메뉴/정책에 따릅니다.

## 서비스 워커와 데이터 경계

추가 런타임 라이브러리 없이 `build/pwa-plugin.ts`가 프로덕션 빌드의 `sw.js`를 생성합니다.
개발 모드에서는 SW를 등록하지 않습니다. 프로덕션에서도 보안 컨텍스트와 지원 환경에서만
등록하며, 준비 실패·오프라인·새 버전 상태는 `PwaStatus`에서 안내합니다.

앱 번들/HTML/공개 에셋과 워커 구현의 내용 해시를 버전에 포함합니다. 설치 시 해당 빌드의
HTML·JS·CSS·로컬 폰트·아이콘·기본 이미지·공개 출처 고지를 모두 precache합니다.
이번 빌드의 목록은 30개입니다. `verify-pwa-build.mjs`가 빌드 후 모든 지연 청크·폰트·아이콘이
목록과 실제 파일에 있는지 검증합니다. 폰트 용량 때문에 일부 청크가 빠지지 않도록 고정
2MB 제한을 두지 않았으며 캐시 설치 실패 시 새 캐시만 제거합니다.

범위 내 내비게이션은 현재 SW 버전의 `index.html`, 목록에 있는 정적 파일은 해당 캐시를
우선 반환합니다. 네트워크 응답을 무제한 runtime cache로 추가하지 않습니다.
외부 출처, 알 수 없는 URL, query가 붙은 에셋 요청, POST, Blob URL, ZIP, API 응답은
워커 캐시 대상으로 넣지 않습니다. HTML/에셋 캐시와 기존 사용자 IndexedDB는 별개입니다.
워커는 IndexedDB를 열거나 삭제하지 않으며 DB 모델·버전·Repository는 변경하지 않았습니다.

새 버전은 다음과 같이 처리합니다.

1. 등록/창 포커스/매시간 연결 상태에서 `updateViaCache: none`으로 업데이트를 확인합니다.
2. 설치 완료 후 waiting 상태에서 안내합니다. 입력 중 자동 새로고침이나 skipWaiting은 하지 않습니다.
3. 식물·관리·일기 화면과 백업 화면에서는 적용을 막아 진행 중 입력/작업을 보호합니다.
4. 사용자가 다른 화면에서 ‘업데이트 적용’을 누르면 워커가 같은 origin의 창 수를 확인합니다.
   여러 창이 열려 있으면 닫으라는 안내 후 대기하고, 한 창이면 활성화합니다.
5. 활성화 시 `leafory-shell-` 접두사의 이전 버전 캐시만 삭제하고 현재 창을 다시 엽니다.
   다른 앱 캐시나 사용자 IndexedDB는 건드리지 않습니다. 모든 앱 창이 닫힌 경우에는
   브라우저의 정상 SW 생명주기에 따라 새 버전이 자연 활성화될 수도 있습니다.

초기 precache가 끝난 뒤에는 로컬 식물/사진/일기/관리 기록·캘린더·ZIP 생성/복원을
오프라인에서 사용할 수 있습니다. 외부 분류 출처 보기, 설치 파일의 최초 다운로드와
새 버전 다운로드는 연결이 필요합니다. 연결 안내는 브라우저의 online/offline 신호를
사용하므로 인터넷 케이블 단절과 특정 서버 장애를 완전히 구분하는 진단 기능은 아닙니다.
저장소 용량/OS 정리 정책에 따른 캐시 제거까지 영구 오프라인을 보장하지는 않으며 ZIP 백업은 유지합니다.

## 번들 비교

단위는 kB(1000 bytes). Phase 7 프로덕션 빌드와 이번 빌드를 비교했습니다.

| 항목              | Phase 7              | Phase 8                 |
| ----------------- | -------------------- | ----------------------- |
| 시작 index JS     | 502.30 (gzip 155.51) | 약 366.50 (gzip 115.62) |
| 별도 초기 공통 JS | 없음                 | 약 103.61 (gzip 34.08)  |
| 초기 정적 JS 합계 | 약 502.30            | 약 470.13               |
| 백업 별도 청크    | 28.72                | 약 28.59                |
| 개별 500kB 경고   | 있음                 | 없음                    |

시작 파일만 비교하면 약 27%, 실제 초기 정적 JS 합계는 약 6.4% 감소입니다.
`verify-pwa-build.mjs`가 초기 정적 import 그래프를 따라 합계를 출력하므로 공통 청크를
빼고 큰 폭으로 개선된 것처럼 계산하지 않습니다. 파일 크기/압축 도구 차이로 소수점 차이는 있습니다.

식물 등록/수정, 관리 기록 편집, 사진 일기 작성/수정/상세가 경로별 lazy loading입니다.
기존 백업·캘린더 별도 청크는 유지했습니다. 초기 파싱/실행 범위를 줄였지만 PWA의
미방문 화면까지 오프라인 지원하기 위해 SW가 지연 청크도 백그라운드에서 다운로드합니다.
따라서 전체 최초 설치 다운로드 용량이 그만큼 줄었다는 의미는 아닙니다.

## 검증 결과

- Phase 7 커밋 전 248개 테스트, 타입·린트·포맷·빌드 재검증 통과.
- Phase 8 전체 267개 테스트(27개 파일), 타입·린트·포맷·빌드 통과.
- 신규 19개: worker precache·설치 실패·이전 캐시 정리·오프라인 HTML/지연 청크,
  외부/비공개/ZIP/Blob/POST 제외, 다중 창 업데이트, Manifest/PNG 실제 크기,
  폼에서 업데이트 차단, 오프라인 안내, 설치 안내 화면.
- 기존 식물/대표 사진·사진 일기·관리 기록·백업·캘린더 회귀 테스트를 모두 유지했습니다.
- 실제 IAB 프로덕션 origin `http://127.0.0.1:4174`에서 준비 완료를 확인했습니다.
  원래 5173과 Phase 7 검증용 5174 DB는 접근/초기화하지 않았습니다.
- 4174에서 검증용 식물 1개를 만들고, **preview 서버를 종료**한 뒤 새로고침했습니다.
  아직 방문하지 않았던 일기 화면을 열어 프로젝트의 생성된 몬스테라 이미지 1장을 첨부하고
  제목/메모를 저장했습니다. 새로고침 후 사진 Blob과 일기 복원을 확인했습니다.
- 서버가 없는 상태에서 홈 물주기를 저장하고 미방문 캘린더/백업 경로를 열었습니다.
  사진·일기·관리 기록이 각 1개로 조회되고 ZIP 생성 후 다운로드 링크가 만들어졌습니다.
- 이후 빌드 산출물 SW의 캐시 버전만 임시 변경해 배포 업데이트를 모의했습니다.
  새 버전 안내, 폼 적용 비활성화, 2개 창에서 적용 거절, 다른 창을 닫은 뒤 업데이트와
  사진·일기·식물·관리 기록 각 1개 보존을 확인했습니다. 임시 SW는 최종 빌드로 재생성합니다.
- 서버를 다시 끄고 앱 창을 닫았다가 새 창 `/calendar`로 열어도 기록이 복원됐습니다.
  이는 실제 서비스 워커를 통한 서버 부재 테스트이며, 모바일 비행기 모드 실험은 아닙니다.
  offline 이벤트 안내는 자동 테스트로 확인했습니다.
- 320×740·390×844 캡처를 생성했고 가로 넘침이 없습니다. 물리 iPhone/Android의 설치,
  standalone 실행, 카메라·파일 앱·ZIP 다운로드/복원은 아직 실기기 체크리스트 대상입니다.
  native 파일 선택 도구가 오래 대기했지만 사진 첨부 자체는 완료·검증했습니다.
- 테스트용 4174의 식물/사진/일기/관리 기록은 남겨 두었습니다. 사용자 데이터는 삭제하지 않았습니다.
- 기능 구현 시점에는 Phase 8을 커밋·push하지 않았습니다. 이후 마무리 Git 정리에서 커밋·push합니다. HTTPS 인증서 설치나 인터넷 배포는 실행하지 않았습니다.

## 마무리: 안내 문구와 실기기 준비

오프라인 활성화 안내는 캐시 보존이나 모든 기기에서의 영구 동작을 보장하지 않도록
수정했습니다. 최초 온라인 접속과 앱 파일 저장 완료, 파일/로컬 기록이 남아 있는 조건,
브라우저의 캐시 정리 가능성 및 사진/파일 선택기의 기기별 차이를 설명합니다.
로컬 저장만 제공하며 계정/클라우드 동기화가 없다는 안내를 명시했습니다.
서비스 워커·DB·기능·디자인은 이 마무리 작업에서 추가/변경하지 않았습니다.

[모바일 테스트 문서](mobile-testing.md)에 Vercel Preview와 인증된 로컬 HTTPS 터널 비교,
고정 origin·접근 보호·인증 세션·사진 촬영·비행기 모드 저장·ZIP 다운로드/복원 절차를
추가했습니다. HTTPS 인증서 설치·외부 배포·터널 실행은 하지 않았고 실제 사용자 데이터는
삭제하거나 초기화하지 않았습니다. 기존 캡처는 기능 구현 당시의 문구이며 마무리 문구
캡처를 별도로 보관했습니다.

마무리 재검증에서도 타입·린트·포맷·267개 테스트·빌드 및 30개 precache 파일 검증을
통과했습니다. 최종 시작 JS는 약 366.59kB, 초기 정적 JS 합계는 약 470.22kB이며
500kB 경고는 없습니다. 별도 로컬 origin 4180에서 320px/390px의 가로 넘침 없음과
Pretendard를 확인했습니다. 문구 검증 과정에서는 사용자 기록/사진을 입력·삭제·복원하지 않았습니다.
